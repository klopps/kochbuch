# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Kochbuch is a mobile-first recipe web app and app (PHP/MySQL backend, Bootstrap/JS frontend, Capacitor-wrapped for Android/iOS, installable as an offline-capable PWA). Users create recipes (ingredients scaled per portion count, step-by-step instructions, difficulty, prep/rest/cook times, calories, allergen notes, diet flags, images, source link, public/private visibility, tags), organize any recipe (their own or others' public ones) into custom categories to build a personal cookbook, search, and share a recipe via link. Recipes export as JSON/PDF/XML. Multilingual UI (German + English to start), role/rights-based access, light/dark theming.

It is deliberately built to the same technical conventions — and, as far as reasonably possible, the same directory structure — as the sibling project **YTAN** (`c:\dev\www\ytan`, `https://github.com/klopps/ytan`) — Kochbuch's own `todo.md` calls this out explicitly for the stack in general, and specifically for user management and the translation tooling ("Benutzerverwaltung soll der des Projekts YTAN entsprechen", "Übersetzungen ... siehe YTAN"). Read `c:\dev\www\ytan\CLAUDE.md` for the fully-realized version of these patterns before implementing the equivalent Kochbuch feature — don't reinvent a shape YTAN has already solved. The sections below summarize the concrete parts of that reference worth carrying over; when in doubt, go re-read the actual YTAN source rather than relying on the summary.

The scaffold plus a working recipe/category UI exist (see `done.md`): a booting Slim app, JWT login, the full `user`/`recipe`/`category`/`tag` schema, a Bootstrap 5 frontend (recipe list/search/detail/create/edit, categories, login, portion scaling, image upload, JSON/XML/PDF export, DE/EN language switcher, light/dark theming), and a working PHPUnit suite — laid out under the same top-level directories YTAN uses (`src/`, `public/`, `templates/`, `resources/i18n/`, `database/migrations/`, `tests/{Unit,Integration,Fixtures}/`, `docs/`, `bin/`). No AdminLTE admin area, admin user management/invite flow, translation-editing UI, or Capacitor/PWA setup yet — those stay "planned" below until built.

## Tracking work (todo.md, done.md)

Same convention as YTAN. The repo-root `todo.md` is the running record of open feature work and notable pending fixes — every new feature and every larger change must be noted there automatically, without the user having to ask. It holds only a single top-level `# Offene Punkte` section, each open item its own `##` heading. The repo-root `done.md` (create it once the first item is finished — it doesn't exist yet) holds the completed counterpart: a single top-level `# Erledigt` section, same one-`##`-heading-per-item convention. A still-open request stays under `todo.md`'s `# Offene Punkte`; once it's done, move its heading out of `todo.md` entirely and append it to the top of `done.md`'s `# Erledigt` section. A closed item's body follows YTAN's style: the original request struck through (`~~...~~`) followed by `Gelöst (YYYY-MM-DD): ...` with a substantive explanation of what was actually built/fixed — enough detail that the *why* and *how* survive independently of git history.

`todo.md` currently predates this convention (plain feature-description headings, no `# Offene Punkte` wrapper) — reformat it to match the next time it's substantially edited, rather than leaving new items in the old style alongside it.

## Commands

```bash
composer install
cp .env.example .env              # fill in DB credentials, JWT_SECRET
php bin/migrate.php               # applies database/migrations/*.sql in filename order
php -S localhost:8000 -t public public/index.php
```

- Adding a schema change: add a new plain-SQL file `database/migrations/NNN_description.sql` (zero-padded, next number) — no migration framework, `bin/migrate.php` just runs un-applied files in sorted order once each.
- No frontend build step — `public/js/*.js` are plain scripts loaded directly by `templates/app.php`, no bundler/transpiler/package.json (until Capacitor tooling is added, see below).
- The plain `php`/`composer` on PATH on this dev machine resolve to PHP 7.4, which fails composer.json's `>=8.1` platform check — use `C:\dev\php8\php.exe` (with `C:\ProgramData\ComposerSetup\bin\composer.phar` for Composer itself) for anything version-sensitive, same as YTAN.
- **Auto-generated build version** (ported 1:1 from YTAN): `composer install`/`composer update` run `bin/configure-git-hooks.php` (`post-install-cmd`/`post-update-cmd`), which sets `git config core.hooksPath .githooks` — a no-op outside a real git checkout, e.g. `bin/deploy.bat`'s build copy. That activates `.githooks/pre-commit`, a plain shell script (runs under Git Bash on Windows too) that regenerates the repo-root `VERSION` file (`YYMMDD-HHMM-<short hash of the parent commit>`, UTC) and `git add`s it into the very commit being made, every commit. `src/App.php`'s `/` route reads it into `$appVersion` (`'dev'` if missing), `templates/app.php` shows it centered at the bottom of the nav drawer. `VERSION` sits outside `public/` (not web-accessible) and is deliberately *not* excluded from the deploy package, since the remote copy has no `.git` to derive it from. If a fresh clone's commits don't update `VERSION`, re-run `composer install` or set `core.hooksPath` by hand.
- `composer test-db` (= `php bin/setup-test-db.php`) clones the dev database's current structure into `<DB_DATABASE>_test`; re-run it after any schema change outside a normal `bin/migrate.php` run against the test DB too.
- `JWT_SECRET` must be at least 32 bytes (`AuthService`'s constructor throws a clear `RuntimeException` at boot otherwise) - `firebase/php-jwt` >=7 rejects shorter HS256 keys since CVE-2025-45769. Generate one with `php -r "echo bin2hex(random_bytes(32));"`.
- Vendoring a new `public/lib/*` library: fetch it from `cdn.jsdelivr.net/npm/<pkg>@<version>/...` with `curl`/`Invoke-WebRequest` into the right subdirectory (see `public/lib/README.md`) - that's how Bootstrap 5.3 and Bootstrap Icons already got there, no npm/package.json involved.

## Backend architecture (follow YTAN's shape)

Mirrors YTAN's `src/App.php` / `src/Http/Controllers/*` / `src/Domain/*` layout:

- **Framework**: Slim 4, PSR-7 (`slim/psr7`), PSR-4 autoloading (`Kochbuch\` → `src/`). No DI container — wire everything by hand in `src/App.php`'s `App::create()` (PDO connection, repositories, services, controllers constructed and closed over directly; flat `$app->get/post/put/delete(...)` route registrations).
- **Auth**: stateless JWT bearer tokens (`firebase/php-jwt`), not PHP sessions — matches the "Session soll theoretisch unendlich bestehen bleiben" requirement much more simply than server-side session state would (a long-lived/refreshing JWT, no session store to expire). `AuthMiddleware` decodes a bearer token into a `"auth"` request attribute without ever rejecting the request itself; controllers call `requireAuthUser()`/`requireAdmin()`/`assertOwnerOrAdmin()` (`BaseController`, same names as YTAN) to enforce access per-endpoint.
- **Recipe visibility** (todo.md "Sichtbarkeitsstatus"): three levels, not just owner/public — `private` (owner/admin only), `internal` (any logged-in user, the default for new recipes), `public` (anyone, including logged-out). `RecipeController::findVisible()` is the single gate all read paths (`show()`, `serveImage()`, `export()`) go through; `RecipeRepository::search()` has its own parallel visibility filter in SQL (can't reuse `findVisible()` there, it checks one already-fetched row) — keep both in sync when this list ever grows past three levels.
- **Data access**: plain `PDO` + `prepare()`/`execute()`/`fetch()`/`fetchAll()` repositories per domain (`src/Domain/{Recipe,Category,User}/*Repository.php`), no ORM/query builder. `RecipeRepository` owns the recipe row plus its child rows (`recipe_ingredient`/`recipe_step`/`recipe_tag`/`recipe_image`) in one place — `create()`/`update()` wrap all of it in a single PDO transaction (`replaceIngredients()`/`replaceSteps()`/`replaceTags()` each delete-then-reinsert the child rows, simplest way to handle a form that can add/remove/reorder rows freely without diffing).
- **Recipe images**: stored outside the webroot under `storage/recipe-images/{recipeId}/` (see `RecipeImageService`, mirrors YTAN's `ImageStorageService` - validates real file bytes via `finfo`, not the client's claimed MIME type; max 5 MB, max 8/recipe), served back through `GET /api/v1/recipes/{id}/images/{imageId}` after the same visibility check as the recipe itself — never a static, guessable URL, since an image can belong to a private recipe. `public/js/api-client.js`'s `imageUrl()` just builds that URL directly (unlike YTAN's private-tour-photo Blob/object-URL dance) because the `<img>` tags are always for a recipe the current page has already loaded and been allowed to see; a *different* user hot-linking that same URL still hits the same visibility check server-side and gets a 403.
- **Migrations**: plain numbered SQL files (`database/migrations/NNN_description.sql`), applied in order by a small `bin/migrate.php`, tracked in a `schema_migrations` table — no migration framework. `001` is the `user`/`user_token` schema, `002` is `recipe`/`recipe_ingredient`/`recipe_step`/`recipe_image`/`tag`/`recipe_tag`/`category`/`category_recipe`.
- **Errors**: `src/Exception/*` (`ApiException` base + `NotFoundException`/`ValidationException`/`UnauthorizedException`/`ForbiddenException`), a central error handler turning any thrown `ApiException` into `{"error": {"message": ...}}` with the right HTTP status.
- **Export**: `RecipeController::export()` (`GET /api/v1/recipes/{id}/export/{json|xml|pdf}`) - JSON is the recipe's own `find()` shape pretty-printed; XML is a generic recursive array→`SimpleXMLElement` walk; PDF goes through `dompdf/dompdf` (already a YTAN dependency for its own Touren-Dokument PDFs) rendering a small inline HTML string, no separate template file. All three always use the recipe's base `servings` amount, matching the JSON API - portion scaling is a client-side-only display concern (see Frontend architecture).
- **Roles/rights**: flat boolean columns on `user` (YTAN's `is_admin`, `tour_create`, etc. convention) rather than a permissions table, unless Kochbuch's role model turns out to need more than a handful of flags.

## i18n (mirror YTAN's Translator/TranslationRepository)

- One flat `key => string` JSON file per locale under `resources/i18n/{locale}.json` (`de.json`, `en.json` — exist, currently a handful of starter keys), shared as the single source of truth between server-rendered PHP and client JS.
- `src/Service/Translator.php` (read path, every request, **built**): loads the active locale's file plus a fallback locale's file, `t($key, $vars)` resolves active → fallback → the key itself, `{var}` substitution via `strtr()` (values must already be escaped by the caller). Locale resolution order: stored `settings` cookie → `Accept-Language` header → default (`de`).
- Client side (**built**): the resolved locale's full string map is injected once as `window.KOCHBUCH_TRANSLATIONS` (see `templates/app.php`) and read by `public/js/i18n.js`'s `t()`/`translateApiError()`. The navbar's DE/EN button pair (`public/js/settings.js`'s `setLanguage()`, wired in `nav.js`'s `wireLanguageSwitcher()`) is todo.md's "Benutzer können ihre bevorzugte Sprache wählen" - it writes the choice into the same `settings` cookie `Translator::resolveLocale()` reads server-side, then does a full `location.reload()` (unlike the theme toggle, the active language is baked into the page server-side, so there's no in-place client update possible).
- `TranslationRepository` (write path, admin-only, separate from the hot read path — **not built yet**): will load/save the JSON files for the admin translation tool, refuse to save if the locale files' key sets diverge (unless forced) and refuse any value containing `</script` (values get embedded in a `<script>` tag on every page load) — mirror YTAN's `src/Service/TranslationRepository.php` exactly, it already solves this.
- The admin translation UI (**not built yet**) will be a dedicated `/admin/translate` page/tool, editing both locale files side by side and surfacing key-mismatch errors from `TranslationRepository`.

## Planned admin area (AdminLTE, mirror YTAN's `/admin/*`)

Per `todo.md`: a separate admin surface built on AdminLTE (vendored under `public/lib/adminlte/`, not npm — same as YTAN), distinct from the main app's own UI. Follow YTAN's structure:
- One shared shell (`templates/partials/admin-shell-header.php` / `-footer.php`) that every `/admin/*` page includes; a new admin tool is a new route + template + one entry in the shell's nav-items array, not a one-off layout.
- Routes gated server-side (`requireAdmin()`), so the pages themselves are only reachable at all once logged in as an admin — no separate client-side gate to keep in sync.
- Minimum pages for Kochbuch: `/admin` (dashboard), `/admin/users` (user management, see below), `/admin/translate` (translation tool, see above). Not to be confused with the already-built `#/categories` screen (`public/js/views/categories.js`) — that's each logged-in user's own private "my categories" grouping (todo.md's "Kategorien" feature), not an admin tool.

## Planned user management (mirror YTAN)

Follow YTAN's `User` domain shape: a `user` table with flat rights columns, JWT claims carrying the fields a request needs to authorize itself (`sub`, `username`, `email`, `is_admin`, plus whatever Kochbuch-specific rights emerge) minted through one shared `issueToken()` so the claim shape never drifts between login/invite/password-reset. Invite and password-reset both funnel through a single-use `user_token` table (`purpose` = `invite`/`reset`) and a signed-out-accessible `/set-password?token=...` landing page, exactly as YTAN does — don't invent a second token mechanism for one of the two flows.

## Frontend architecture

- **Mobile First**, per `todo.md` — always check the mobile viewport (e.g. ~390×844) before desktop when testing any UI change. Concretely bit once already: a 5-across Bootstrap grid row (ingredient name/amount/unit/note/remove in `recipe-form.js`) clipped every field's placeholder text and cut the remove button off-screen at 390px even though `document.documentElement.scrollWidth` never exceeded the viewport (narrow columns, not overflow) — fixed by switching that row to `d-flex flex-wrap` with per-field `min-width`/`width` instead of `col-N` grid classes, so the row wraps onto multiple lines on narrow screens instead of squeezing every column.
- **Bootstrap 5.3 + Bootstrap Icons 1.11** (**vendored**, `public/lib/bootstrap/`, `public/lib/bootstrap-icons/` — fetched from `cdn.jsdelivr.net/npm/...`, see `public/lib/README.md`) for layout/components (this differs from YTAN, which hand-rolls its own CSS — Kochbuch's `todo.md` explicitly calls for Bootstrap). Plain `<script>`/`<link>` tags, no build step, same "no bundler" spirit as YTAN.
  - **Re-theming Bootstrap's brand color**: setting `--bs-primary` on `:root` is *not* enough — Bootstrap's compiled `bootstrap.min.css` bakes its blue into each component's own local custom property at build time (e.g. `.btn-primary{--bs-btn-bg:#0d6efd;...}`), not a live read of `--bs-primary`. `public/css/style.css`'s "Bootstrap component re-theming" block explicitly overrides `--bs-btn-bg`/`--bs-btn-hover-bg`/etc. on `.btn-primary`, `.form-check-input:checked`, `.form-control:focus`/`.form-select:focus`, and `.dropdown-item.active` — extend that list (not `--bs-primary` itself) when a new Bootstrap component using the primary color shows up unthemed.
  - **Dark mode**: `public/js/settings.js`'s `applyTheme()` sets both our own `[data-theme]` (custom tokens) and Bootstrap 5.3's native `[data-bs-theme]` on `<html>` together, so Bootstrap's own dark-mode component styles (cards, offcanvas, forms, dropdowns) follow the same toggle as the rest of the app without any extra work.
- **API access** (**built**): all backend calls go through `public/js/api-client.js`'s `Kochbuch.get/post/put/del/upload/download(...)` singleton (mirrors YTAN's `Ytan` object) — don't `fetch()` the API directly from feature code. `upload()` sends `FormData` (recipe image uploads) without manually setting `Content-Type` (the browser needs to add its own multipart boundary); `download()` attaches the auth header itself and triggers a Blob-based browser download, since a plain `<a href>` can't send an `Authorization` header (needed for exporting a *private* recipe).
- **Dark/Light theming** (**built**): CSS custom properties on `:root` (light) and `:root[data-theme="dark"]` (dark) in `public/css/style.css`, every color routed through a token; `setTheme()`/`applyStoredTheme()` persist the choice in a `settings` cookie (also read server-side by `Translator::resolveLocale()`) and apply it as early as possible in page load to avoid a flash of the wrong theme.
- **Subdirectory-safe** (**built**): `src/App.php` derives `$baseUrl`/`$app->setBasePath()` from `$_SERVER['SCRIPT_NAME']` rather than hardcoding absolute paths, injected client-side as `window.KOCHBUCH_API_BASE` — mirrors YTAN's `$baseUrl`/`window.YTAN_API_BASE`.
- **`Cache-Control: no-store` on every server-rendered HTML route** (`/`, `/imprint`, `/privacy`) — without it, a browser can serve a stale cached copy of the page whose `<script src="...?v=OLD_MTIME">` tags point at an equally stale cached asset, silently defeating `App::assetVersion()`'s cache-busting. Discovered while iterating on the UI: edits kept appearing not to take effect in the browser even though `curl` showed the server had the new file — `Cache-Control: no-cache` alone wasn't reliable here since there's no `ETag`/`Last-Modified` for the browser to revalidate against. (Separately: a same-origin navigation that only changes the URL *hash* — e.g. `#/recipes` → `#/recipes/new` — never re-fetches the document at all, by design; that's the hash router's whole point, but it can look identical to a stale-cache bug when you're manually testing. A real reload, or a change to the path/query, is the only way to observe a fresh page load.)
- **No SPA framework/router library** — `public/js/router.js` is a ~40-line hash router (`Router.on(pattern, handler)`/`Router.navigate(path)`, `:param` segments, a `?query=string` suffix parsed separately). Register a literal route (e.g. `/recipes/new`) *before* the parameterized route it would otherwise be swallowed by (e.g. `/recipes/:id`) — see the registration order in `public/js/app.js`.
- **Views**: `public/js/views/*.js`, one file per screen (`recipes-list`, `recipe-detail`, `recipe-form`, `categories` [list + detail], `login`, `not-found`), each a plain function that builds an HTML string and assigns it to `#app`'s `innerHTML`, then wires event listeners. `public/js/helper.js` holds cross-view helpers (`escapeHtml()`, `formatAmount()`, `recipeCardHtml()`/`recipeGridHtml()`, difficulty/diet badge builders, `loadCurrentUser()`/`isOwner()`). No shared component/templating library — a new view follows the same "template string + innerHTML + querySelectorAll" pattern as the existing ones.
- **Portion scaling** (`recipe-detail.js`): purely client-side display, never round-trips to the API — the portion stepper re-renders `recipe.ingredients` scaled by `currentServings / recipe.servings` (`formatAmount()` rounds to 2 decimals, trims trailing zeros) each time it changes. The backend always stores/returns amounts for the recipe's own base `servings`, including in exports.
- **Recipe image upload UX**: only available once a recipe has an id, i.e. after the first save — `recipe-form.js` doesn't attempt pre-id upload; saving a new recipe redirects straight to its detail page (`recipe-detail.js`), whose image gallery (owner-only "+" tile) is where images actually get added.

`templates/app.php` is the SPA shell: injects translations/API base/locale, loads Bootstrap + `public/css/style.css`, the navbar (Bootstrap navbar + offcanvas: only the brand, linking to `#/recipes`, stays in the top bar; auth-area/language-switcher/theme-toggle/legal-links live in the burger drawer at *every* width, desktop included — deliberately no `navbar-expand-*` class; there are no separate nav links, category management is reached via the gear button next to the recipe list's category dropdown), an empty `<main id="app">` the router renders into, and a `#toastHost` (`public/js/toast.js`, Bootstrap Toast wrapper for save/delete/error feedback).

## Planned mobile/offline (Capacitor + PWA)

- **Capacitor**: a `capacitor.config.json` pointing at the live web app URL (`server.url`), `webDir` set to the PHP app's public root — the native shell loads the real deployed site in a WebView rather than bundling a separate copy, same as YTAN's `capacitor.config.json`/`android/` setup. Add `ios/` alongside `android/` (YTAN currently only has the Android project set up) once iOS packaging is needed.
- **PWA + offline**: a web app manifest and a service worker caching the app shell (and ideally already-viewed recipes) for offline use — this has no YTAN precedent to copy (YTAN is not built as a PWA), so this piece needs its own design rather than a port.

## Testing

Same split as YTAN. **Built and passing** (19 tests): PHPUnit (`tests/Unit/`, `tests/Integration/`, `tests/Fixtures/`) against a dedicated `<db>_test` database (never the dev DB, set up via `composer test-db` = `bin/setup-test-db.php`, cloning the dev DB's structure), every test wrapped in a rolled-back transaction (`tests/TestCase.php`); `tests/Integration/ControllerTestCase.php` calls a `*Controller` method directly with a constructed PSR-7 request rather than going through Slim's router/`AuthMiddleware` — an `ApiException` a controller throws propagates straight to the test (use `expectException()`/try-catch, not `decode()`, for those cases). Run with `composer test` (needs PHP 8.1+ on PATH — see the deploy script comments for this machine's `C:\dev\php8\php.exe` situation).

- **Repositories built on `$this->pdo`, never `Connection::fromEnv()`**: `TestCase::setUp()` opens the outer transaction on one specific PDO instance (`$this->pdo`); a repository built on a *second* connection (`Connection::fromEnv()`) can't see that transaction's still-uncommitted rows at all (a real MySQL isolation guarantee, not a bug) - `AuthControllerTest`'s first draft got exactly this wrong (login "failed" because the just-inserted test user was invisible to the second connection) before being fixed to use `$this->pdo`.
- **PDO has no real nested transactions**: any repository method that manages its own transaction (`RecipeRepository::create()`/`update()`, wrapping the parent recipe row + ingredient/step/tag child-row writes atomically) must check `$this->pdo->inTransaction()` before calling `beginTransaction()` - otherwise it throws the moment it's exercised from inside `TestCase`'s own outer transaction. The fix (`RecipeRepository::beginTransaction()`, a private wrapper returning whether *this* call owns the commit/rollback) only starts/commits/rolls back when no transaction is already active, so the exact same code path works standalone (a real request, own connection, no outer transaction) and inside a test (already-active outer transaction, whose `tearDown()` rollback is the one that actually runs). Any future repository with its own transaction needs the same wrapper.
- **Not built yet**: Playwright e2e (`tests/e2e/`) against its own separate `<db>_e2e` database, for frontend flows PHPUnit can't reach.
- Add/update a PHPUnit test in the same change that adds/changes backend logic — don't leave coverage for later (see `tests/Integration/{Auth,Recipe,Category}ControllerTest.php`/`tests/Unit/AuthServicePasswordValidationTest.php` for the pattern).
